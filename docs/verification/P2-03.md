# P2-03: durable tasks and queue

Status: complete.

Environment: local macOS workspace, Rust 2021. Date: 2026-10-18.

Added `EventLog::append_with` to commit a caller's database mutation and its redacted event in
one transaction. Subscribers are notified only after commit. Existing `append` uses this path.

The new tests first failed to compile because `append_with` did not exist.
`cargo test -p mote-eventlog --lib` passed: 14 passed, 0 failed.

Tests prove a successful mutation commits with a redacted event, a failed mutation leaves neither
its database changes nor an event, and projection failure rolls back an attached mutation.
Failure cases deliver no event to subscribers.

Added the first `HrnsStore` slice with scoped durable tasks, revision-checked transitions, FIFO
promotion and a database constraint that permits only one active task. The store refuses an
event log backed by a different database.

`cargo test -p mote-eventlog -p mote-hrns` passed: 27 tests passed, 0 failed across the two
crates, including five store tests. The store cases cover restart recovery, concurrent enqueue,
concurrent promotion, scope isolation, stale revisions, duplicate IDs and injected event
projection failure. The injected failure proves that the task update and its transition event
roll back together.

This first pass proved the durable task queue foundation, before action and checkpoint storage
was added in the follow-up below.

Follow-up on 2026-10-18 added durable scoped actions and checkpoints. Action transitions use
revision guards and the same atomic event path. Checkpoints advance monotonically, must match
the stored task state and cannot reference an action from another task. Reopening the store
retains both records. `cargo test -p mote-hrns --test store` passed: 7 passed, 0 failed. The two
new cases also inject an action-event failure and prove that no partial action transition or
checkpoint event remains.

Actions and checkpoints are now implemented. The criterion remains open only for the driver
recovery and one-active-task behavior across every persisted checkpoint.

## One-step driver and recovery

The driver follow-up added FIFO activation, harness selection, cancellation, checkpointed model
steps and an idempotent action-executor boundary. Completion text and input questions survive
restart. Tool proposals bind the exact task revision and commit their action, checkpoint and
redacted event atomically. A stale model response cannot create an action.

`cargo test -p mote-hrns` passed 24 tests: 4 contracts, 6 driver, 10 store and 4 transition
tests. The driver fixtures cover both harnesses, every persisted task state, interrupted action
and terminal checkpoints, harness failure, cancellation, one active task, FIFO order and an
executor failure after an effect but before the action commit. Retrying by stable action ID
produces one effect. A store fixture proves a model step, state transition and checkpoint all
roll back when event storage fails. Another proves the stored transition event is redacted.

The required final gates passed on the same checkout:
