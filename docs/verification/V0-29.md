## Bugs fixed to make the path work reliably
1. `moted mcp` crashed when the data dir did not exist (now ensured) - OpenCode otherwise saw no tools.
2. MCP `initialize` hardcoded `protocolVersion`; now echoes the client's.
3. `run_opencode` sets stdin to null and a timeout.
4. Root cause of the earlier timeouts: OpenCode's GLOBAL config (`~/.opencode/opencode.json`,
   provider lmstudio -> 127.0.0.1:1234, refused) overrode the per-run config, so OpenCode tried a
   dead endpoint and hung. Fixed by passing `--dir <cwd>` and `--model ollama/qwen3-coder:30b-64k`
   so the right provider/model is used. After the fix: 3/3 runs complete, 0 timeouts.

## Result (clean, warm, uncontended)
- answer via MCP `moted_file_read` = true; file content returned correctly.
- first-token p50 = **9.25 s** over 3 completed runs, 0 timeouts. Gate is 3 s -> MISS.

The capability ("reads a file through file_read and answers") is fully verified and reliable.
The latency gate is missed: the first streamed text token is the post-tool-loop answer, and each
turn cold-starts a fresh `opencode run` process (Bun startup + MCP spawn + handshake) which
dominates the ~9 s; the model's own generation is ~350 ms warm (per OpenCode part timestamps).

Per v0.md ("If a measured number misses its target, record the number in the evidence file and
leave the item open"), V0-29 is recorded as a measured miss and left open. Closing it to < 3 s
requires a persistent OpenCode server (opencode serve/attach) so turns avoid the per-invocation
cold start, rather than launching `opencode run` per turn - a harness optimization (backlog).
