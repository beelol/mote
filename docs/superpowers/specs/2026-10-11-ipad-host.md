# Native iPad host design

Approved by the owner on 2026-10-11.

## Outcome

Mote ships as a native iPad app whose interface is the same Rust immediate-mode Matrix consumer
used on the Mac. The first deployed app connects securely to one or more Mote hosts. The owner's
Mac is the first host. It owns the agent, models, browser, memory, event log, approvals, Matrix
generation and validation. The iPad renders committed surfaces, sends typed interactions and lets
the owner answer approval cards.

The first delivery order is fixed:

1. Preserve the existing Mac client and Unix socket.
2. Extract a shared Rust Matrix consumer core and a transport-independent host protocol.
3. Run the gallery and a checked-in dashboard in the iPad Simulator.
4. Pair the simulator with `moted` on the Mac through the secure network gateway.
5. Generate validated Matrix surfaces from natural-language requests.
6. Run a browser-backed request and answer its approval card from the iPad.
7. Verify touch, local-network permission, accessibility and recovery on a physical iPad.
8. Create a new Mote App Store Connect record and distribute the verified client through
   internal TestFlight.

Simulator success is required before App Store Connect work. Physical-device success is required
before TestFlight upload. A gallery-only build does not satisfy the deployed app criteria.

## Current distribution phase

## Architecture

### Host authority

A Mote host is the source of truth. It owns model calls, browser profiles, memory, configuration,
event history, approval state, Matrix source, validation and committed consumer surfaces. Every
model call still goes through the ledger. Every stored event still passes through redaction.

The iPad is a thin consumer. It owns only transient interaction state and a small paired-host
directory. It does not run Ollama, read browser profiles, validate untrusted Matrix source or keep
an independent authoritative event history. It renders only a committed, versioned consumer
snapshot from the selected host.

### Shared components

The implementation will separate these responsibilities:

- A shared Rust Matrix consumer core owns rendering state, typed interaction production, Vector
  theme behavior, structural identity and cross-target fixtures.
- A versioned protocol crate owns request, response, event, surface, approval, cursor and error
  envelopes. It has no socket or UIKit dependency.
- The existing Unix transport remains the private local Mac transport.
- A network gateway in `moted` exposes the same protocol over an encrypted paired connection.
- A host transport interface lets the desktop client, iPad client and future relay select a
  transport without changing Matrix semantics.
- A small native iOS shell owns the application lifecycle, entitlements, local-network permission,
  Bonjour discovery, secure credential storage, background transitions and the Rust view entry.
- Browser automation remains a Mac-host worker. Browser page content never becomes executable UI
  source on the iPad.

Rust remains the primary renderer path. A Swift or Objective-C renderer is not authorized merely
because the outer iOS shell uses Apple APIs. Any renderer alternative still requires the evidence
and owner decision in UI-44.

## Host identity and multiple locations

Each host has a stable host ID and a long-lived public identity key. A user-visible name and optional
location label help distinguish hosts such as Home Mac, Office Mac and Cloud Mote. Network addresses
are discovery details and never identity.

The iPad can pair with multiple hosts. Each paired host has independent credentials, protocol
version, last event cursor, selected thread, surface history and pending approvals. Switching hosts
never merges cursors, histories, credentials, surfaces or approval decisions. An event or approval
from one host cannot be replayed to another host even when thread IDs collide.

Bonjour advertises `_mote._tcp` and lets the iPad discover an address and port on the same local
network. Its TXT record exposes only protocol major version and the public gateway fingerprint. The
app accepts that address only after it proves a known host identity or after an explicit first
pairing. Bonjour does not authenticate, encrypt or relay traffic.

The protocol addresses a logical `MoteHost`, not a local Mac path. A later cloud host can implement
the same endpoint. A later cloud relay can route opaque encrypted frames to a home Mac. Remote
discovery may use a signed directory or pairing link. None of those additions may change Matrix
source, consumer snapshots, event semantics or approval rules.

## Pairing and transport security

First pairing is an owner-present action. The Mac displays a short-lived pairing offer using the
existing gateway prefix `MOTE1`. The iPad verifies the offer, pins the host identity and stores its
client credential in the iOS keychain. The host records the paired device and its revocable identity.
A pairing offer is single-use, expires and cannot authorize a different host.

The session protocol reuses the approved gateway design in `docs/reuse/hardware.md`: Noise IK and
IKpsk1 with prologue `mote-gateway-v1`, shared test vectors and a monotonically advancing counter in
message 1. After pairing, both peers authenticate before application frames are accepted. Frames are
encrypted, ordered and bound to the host identity, client identity and protocol version. Identity
changes fail closed. A revoked device cannot reconnect. Secrets, raw browser cookies and local
filesystem paths are never sent to the client. The local carrier remains behind the host transport
interface so a later relay can forward the same opaque Noise frames.

The existing Unix socket remains enabled for same-user Mac clients. The network gateway is a separate
listener and does not relax the Unix peer-credential boundary. The listener binds only to configured
interfaces. Local discovery can be disabled without disabling the Unix client.

## Connection and recovery

The app always shows the selected host and one of connecting, online, offline, incompatible or
identity changed. It never silently fails over to another host.

On reconnect, the app resumes the selected host from that host's saved cursor. Duplicate events are
ignored. If retention has passed the cursor, the host sends `resync` and a complete current snapshot.
An interrupted surface replacement leaves the last complete committed surface visible and inert
with respect to the incomplete candidate. Pending approvals survive reconnect.

The following cases are explicit product states:

- Local-network permission denied. The app explains how to restore access and keeps offline fixtures
  available.
- Host asleep, offline or at a new address. Discovery can update the address only after identity
  proof. Existing rendered content remains labeled offline.
- Host identity changed. The app blocks and requires a new owner-present pairing.
- Protocol version incompatible. Both sides report their supported ranges and do not downgrade past
  an unsupported security or semantic boundary.
- App backgrounded or killed. Relaunch resumes only the selected host's cursor and does not replay an
  interaction that lacks a host acknowledgement.
- Expired event retention. The app replaces local transient state with the authoritative resync.

## Inferred Matrix surfaces

A natural-language request may ask Mote for a dashboard, form or task-specific view. The host gives
an approved local model the versioned Matrix contract and the host-owned binding and action manifest.
The model may return ordinary prose followed by one Matrix surface payload. The payload is parsed,
resolved, type-checked, lowered and validated on the host. Only a complete accepted surface replaces
the previous committed surface.

Invalid source receives at most one diagnostic-bearing retry within the existing surface rate budget.
A second failure keeps the previous surface and returns prose plus a visible diagnostic. Model output
cannot create a host action, binding, approval capability or browser permission. A tap or field edit
does not cause a model call. IPAD-04 carries these requirements into the active board. The related UI
criteria in `docs/backlog.md` remain reference material unless activated by an existing v0 parent.

## Browser boundary

Browser work runs on the selected Mac host in a headed Chrome for Testing profile kept separately for
each character under Mote's data directory. This feature implements only the local Mac mode. Mote
never opens the owner's default Chrome profile and never reads its keychain item. Browser page text
enters the agent only as boundary-marked untrusted tool output. Page instructions cannot authorize
tools or change the current task.

Browsing, reading and filling may run automatically only on an approved site. A form submission,
purchase, message, download, OAuth flow, non-GET request or other outward change creates a durable
approval. Nothing executes until the approval is accepted. The iPad receives the same host-owned
approval card and can approve or deny it. Approval IDs, action hashes, host identity, expiry and
current page state are checked immediately before execution. Stale, altered, denied or expired
approvals fail closed.

The browser suite uses local fixtures for submit, purchase, message, download, OAuth and non-GET
requests, plus an unknown or malformed outward-action verdict. Every fixture must create a durable
approval and remain inert before approval. Denial and expiry remain inert. One approved fixture proves
page-state revalidation and exactly-once execution. The end-to-end journey also proves snapshot, read,
fill, stale-ref refusal, prompt-injection refusal, event and ledger records, redacted HAR, before and
after commit screenshots, and a final Matrix result card. No live purchase or message executes in
this delivery. The broader two-mode browser, handoff, Slack and provider-specific journeys remain in
the backlog.

## Native iPad behavior

The simulator must first show separate Layout, Toggle, Slider, Select, List and Form gallery pages,
the checked-in dashboard and a local fixture surface with touch-sized controls, scrolling, text entry
and selection. Selecting a page replaces the resolved layout immediately. Changed red structural
borders split into square pixels and materialize within 120 ms. Unchanged nodes do not restart and
hit testing uses the new layout on the first frame. Reduced motion swaps immediately with only a
brief red outline pulse. It then connects to the Mac gateway and exercises live chat, a generated
surface, typed interactions and an approval.

Physical iPad verification covers touch edges, scrolling, keyboard appearance, rotation, split view,
background and foreground recovery, system light and dark appearance, reduced motion, Dynamic Type
where the Matrix contract permits it, VoiceOver names and reading order, and the real local-network
privacy prompt. The simulator cannot substitute for device-only permission and touch evidence.

The app declares a purpose string for local-network access and the exact Bonjour service types it
browses. App Transport Security remains enabled. Any local transport exception must be avoided or
narrowly justified and documented.

## Distribution

After device-capable build and physical UI checks, create a new explicit bundle ID for Mote.
It must not reuse or modify another installed app or App Store Connect record. Record the chosen
display name, bundle ID, SKU and team before creation. HOST-05 remains open and is not a prerequisite
for internal distribution under the owner's revised scope. Preserve its pending evidence separately.
The bundle ID cannot be changed after the first build upload.

Create one new App Store Connect app record, configure signing and capabilities, archive the same
paired-host client that passed device verification, upload it, wait for processing and install it
through internal TestFlight. The installed TestFlight build must repeat pairing, live chat, generated
Matrix UI, browser approval, reconnect and host-switch isolation. TestFlight success is recorded only
after the build is installed and exercised, not when upload completes.

No external TestFlight group, App Review submission, public release, cloud spending or cloud relay is
authorized by this design.

The repeatable distribution script has two boundaries. Its default dry run inspects Xcode, the
physical Rust target, selected team, bundle ID, version and build number, existing app identities,
and the expected archive and export commands without changing Apple state. A separate explicit
archive/export invocation builds an `iphoneos` Rust library and signed `.xcarchive`, then exports
an `.ipa` and validates bundle identity, signing and entitlements. Upload is a distinct explicit
invocation. Never put Apple credentials, signing keys or pairing state in the repository or logs.
Retain the Simulator target and tests. The App Store Connect record is created in Apple's website
after the owner confirms the unique identity. Apple's current Apps API explicitly does not create
new app records. An API-assisted collision check or upload may be added only when appropriate
credentials and permissions exist. Do not make record creation an implicit script side effect.

TestFlight distributes the client binary, not a Mac relay. Until a remote route is separately
implemented and verified, the installed app can reach `moted` only when its gateway is reachable
on the local network. A test from another city cannot substitute for that route.

Current Apple constraints were checked on 2026-10-11:

- [Local network privacy](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy)
  requires a purpose string and declared Bonjour service types. The privacy prompt requires a device
  check because the simulator does not reproduce it.
- [App Transport Security](https://developer.apple.com/documentation/security/preventing-insecure-network-connections)
  requires secure connections by default.
- [App record creation](https://developer.apple.com/help/app-store-connect/create-an-app-record/add-a-new-app)
  requires the app record before upload and appropriate App Store Connect access.
- [Xcode distribution preparation](https://developer.apple.com/documentation/Xcode/preparing-your-app-for-distribution)
  states that the bundle ID identifies the app and must be chosen carefully.
- [Build upload](https://developer.apple.com/help/app-store-connect/manage-builds/upload-builds/)
  associates the uploaded bundle ID and version with the app record.
- [App Store Connect Apps API](https://developer.apple.com/documentation/appstoreconnectapi/apps)
  does not create a new app record. Apple directs new app creation to the website.
- [App ID registration](https://developer.apple.com/help/account/identifiers/register-an-app-id/)
  requires an explicit bundle ID for a single app and an authorized team role.
- [Xcode beta distribution](https://developer.apple.com/documentation/xcode/distributing-your-app-for-beta-testing-and-releases)
  supports a TestFlight Internal Only channel after an archive is prepared.
- [Internal testers](https://developer.apple.com/help/app-store-connect/test-a-beta-version/add-internal-testers)
  must be App Store Connect users with access to the app. Internal-only builds stay internal.
- [TestFlight overview](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview/)
  governs build processing, tester access and the 90-day testing window.
- [Rust iOS support](https://doc.rust-lang.org/nightly/rustc/platform-support/apple-ios.html)
  documents `aarch64-apple-ios`, `aarch64-apple-ios-sim` and `x86_64-apple-ios` as supported targets
  that require the Apple SDK and Xcode toolchain.

## Acceptance criteria

The root `README.md` is the completion board. These IDs are unique to this feature:

- HOST-01 defines the transport-independent versioned protocol while preserving the Unix transport.
- HOST-02 defines stable multi-host identity and isolation.
- HOST-03 defines owner-present pairing, mutual authentication, encryption and revocation.
- HOST-04 defines Bonjour discovery and secure local address changes.
- HOST-05 defines cursor recovery, resync, duplicate suppression and explicit connection states.
- IPAD-01 defines the shared Rust consumer and iOS target build.
- IPAD-02 defines the offline simulator gallery and dashboard.
- IPAD-03 defines the paired live simulator journey.
- IPAD-04 defines natural-language Matrix generation and its fail-closed validity gate.
- IPAD-05 defines the local Mac browser fixture and iPad approval journey.
- IPAD-06 defines physical iPad behavior and accessibility.
- IPAD-07 defines the separate app identity, signing and App Store Connect record.
- IPAD-08 defines installed internal TestFlight verification.
- IPAD-09 defines a device-capable Xcode and Rust build without breaking the Simulator.
- IPAD-10 defines guarded repeatable archive, export and opt-in upload tooling.

Each criterion receives `docs/verification/<ID>.md` evidence with commands or manual steps, output,
environment, date and commit. Rust changes require `cargo test --workspace` and
`cargo clippy --workspace -- -D warnings` before their commit. Simulator evidence includes target,
device runtime, screenshots and driven interactions. Physical-device evidence names the hardware and
OS. TestFlight evidence records the app record, bundle ID, processed build and installed journeys
without storing credentials or private signing material.

## Deferred scope

The cloud host directory, cloud relay, opaque relay routing, remote wake, cloud browser mode, browser
handoff, Slack approval, provider-specific browser cards, external TestFlight, App Store review,
public launch, Android, Raspberry Pi delivery and live purchase or message execution remain deferred.
The protocol and identity model must leave room for hosts in different places, but this feature does
not build or deploy the relay.
